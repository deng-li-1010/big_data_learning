# Apache Doris Join 体系完整梳理（层级清晰版）

官方文档：[Doris Join](https://doris.apache.org/zh-CN/docs/dev/query-acceleration/colocation-join?_highlight=colocate)

先明确**两层级划分**，避免概念混淆：
- **第一层：单机物理执行算子** —— 单节点上具体怎么做关联计算，官方仅实现 2 种：**Hash Join、Nested Loop Join**
- **第二层：分布式数据分布策略** —— 多节点间如何把数据凑到一起再执行Join，共 4 种：**Colocate Join、Bucket Shuffle Join、Broadcast Join、Shuffle Join**

二者关系：4种分布策略是「数据搬运方式」，最终落到每个BE节点上，还是用 Hash Join 或 Nested Loop Join 完成本地计算。

---

## 一、第一层：2 种物理执行算子
### 1. Hash Join（绝对主力，99% 等值关联场景使用）
#### 执行原理
分为两个阶段：
1. **Build 构建阶段**：选取较小的表（右表），以 Join Key 为键，在内存中构建哈希表
2. **Probe 探测阶段**：流式遍历大表（左表），每一行用 Join Key 去哈希表中匹配，命中则拼接输出结果行

#### 核心特性
- **仅支持等值 Join**（`ON a.id = b.id`），不支持非等值条件
- 对数据无序友好，不需要提前排序
- 性能远高于 Nested Loop Join，是 Doris 默认首选算子
- 右表过大时会触发磁盘落溢（Spill to Disk），性能会下降

### 2. Nested Loop Join（NLJ，兜底算子）
#### 执行原理
两层嵌套循环：以左表为驱动表，逐行遍历右表全量数据，逐条校验关联条件，匹配成功则输出。
伪代码逻辑：
```
for each row in 左表:
    for each row in 右表:
        if 满足Join条件:
            输出结果
```

#### 核心特性
- **支持所有关联场景**：等值、非等值（`> < >= <=`）、笛卡尔积，是通用兜底算子
- 时间复杂度 O(N×M)，性能随数据量增长急剧下降
- 仅在驱动表行数极少（通常百行级）、Hash Join 无法处理时，才会被优化器选中

> 补充：Doris 官方并未将 Merge Join 作为独立物理算子提供，有序数据场景下优化器仍优先选择 Hash Join，不存在第三种标准物理Join算法。

## 二、第二层：4 种分布式数据分布策略
MPP 架构下，数据分散在多台BE节点，Join 前必须先把关联数据汇聚到同一节点。Doris 有 4 种搬运策略，**性能从优到劣依次为**：

### 1. Colocate Join（同位 Join，性能天花板）
#### 触发条件
两张表满足：
- 分桶字段完全相同
- 分桶数量完全一致
- 副本数完全一致
- 同属一个 Colocate Group（`colocate_with` 属性相同）

#### 执行逻辑
建表时数据就已经按相同规则打散到对应BE节点，**相同 Join Key 的数据天然在同一台机器上**。查询时零数据传输，每个BE直接在本地执行 Hash Join。

#### 优势
- 完全消除网络 Shuffle，大表关联性能提升数倍
- 无中间数据传输，集群网络压力极小

### 2. Bucket Shuffle Join（桶级单边 Shuffle）
#### 触发条件
Join Key 与左表的分桶字段一致，右表分布不做要求。

#### 执行逻辑
左表数据保持原地不动，只把右表按照左表的分桶规则做一次哈希重分布，发送到对应左表所在的BE节点，再本地执行 Hash Join。

#### 优势
- 只需要重分布右表一张表，网络开销低于双边 Shuffle
- 不需要预先建表对齐分桶规则，使用更灵活

### 3. Broadcast Join（广播 Join）
#### 触发条件
优化器预估右表过滤后数据量很小（通常 MB 级）。

#### 执行逻辑
把右表全量数据，完整复制广播到每一个持有左表数据的BE节点，每个节点都持有完整右表，再本地执行 Hash Join。

#### 优势与局限
- 优点：左表完全不动，实现简单，维度表+事实表场景非常常用
- 缺点：右表不能太大，否则全量广播会打爆网卡和内存

### 4. Shuffle Join（分区 Shuffle，兜底默认）
#### 触发条件
以上三种都不满足时的默认兜底策略。

#### 执行逻辑
左右两张表都按照 Join Key 做全局哈希重分布，相同Key的数据发送到同一台BE，再在每个节点本地执行 Hash Join。

#### 优势与局限
- 优点：通用性最强，任何等值Join都能执行
- 缺点：两张表都要跨节点传输，网络开销最大，性能最低

## 三、核心对比总表
### 物理算子对比
| 算子 | 支持关联类型 | 性能 | 内存开销 | 定位 |
|------|------------|------|---------|------|
| Hash Join | 仅等值 | 高 | 中（构建哈希表） | 主力算子，默认首选 |
| Nested Loop Join | 全部类型 | 低 | 低 | 兜底算子，非等值/小表使用 |

### 分布式策略对比
| 策略 | 网络Shuffle | 触发前提 | 性能排序 |
|------|------------|---------|---------|
| Colocate Join | 无 | 同分组、同分桶规则 | 1（最优） |
| Bucket Shuffle Join | 仅右表重分布 | Join Key = 左表分桶键 | 2 |
| Broadcast Join | 右表全量广播 | 右表数据量小 | 3 |
| Shuffle Join | 左右表双端重分布 | 无特殊前提，通用兜底 | 4（最差） |

## 四、优化器选择优先级与最佳实践
1. **优化器自动选择顺序**：Colocate Join → Bucket Shuffle Join → Broadcast Join → Shuffle Join
2. **工程落地建议**
    - 频繁关联的大表，尽量设置相同分桶键并加入同一 Colocate Group，从根源消除 Shuffle
    - 维度表、字典表尽量控制体积，让优化器自动走 Broadcast Join
    - 非等值关联尽量业务层改写为等值逻辑，避免触发 Nested Loop Join
    - 大表 Join 务必确保走 Hash Join，可通过 `EXPLAIN` 查看执行计划确认
